# Howl Android: решение о следующей подписи

20.10.2026. В текущем кандидате оформления **сохраняется прежняя production-подпись**. Новый production-ключ не создавался; действующие ключи и публичные APK не заменяются.

Рекомендуемый следующий переход — **новый нейтральный сертификат `CN=Howl`, без полей страны и неподтверждённой организации, с ротацией начиная с Android13/API33**. Приложение остаётся `how.vpn.howl`. Этот вариант сохраняет предусмотренный планом путь обновления Android7+ и меняет активного подписанта на современных ОС.

## Что меняется и что остаётся видно

Текущий сертификат: `C=RU,O=vpn.how,CN=Howl VPN`, SHA256 `8627a0876f3baf1dcf3bf7de297398fa65bc6256a8c6ef30132483995730faa7`. Это публичные метаданные сертификата, а не подтверждение страны регистрации оператора.

| Устройства | Подпись будущего общего APK |
|---|---|
| Android7–8, API24–27 | Прежний сертификат в совместимой подписи v2 |
| Android9–12L, API28–32 | Прежний сертификат; раннюю ротацию не включать |
| Android13+, API33+ | Новый активный сертификат через v3.1 и доказанную lineage от старого |

Старый сертификат останется в совместимых блоках и истории. Средства просмотра APK/истории могут показывать `C=RU` и после перехода. Переход не удалит эти сведения из уже опубликованных версий. Ограничения и порог описаны в [AOSP v3.1](https://source.android.com/docs/security/features/apksigning/v3-1); инструменты — [apksigner](https://developer.android.com/tools/apksigner).

Просто отредактировать DN или подписать обновление только другим сертификатом недостаточно для совместимого перехода. Полное отсутствие старого сертификата в новых APK и бесшовное обновление всех нынешних Android7+ нельзя обещать одновременно. Новый applicationId потребовал бы отдельной установки/переноса данных и другой схемы обновления; этот вариант не предлагается.

## Подготовленный безопасный эксперимент

`tools/verify-signing-rotation-lab.py` создаёт два одноразовых тестовых PKCS12-ключа в закрытом временном каталоге. У предшественника лаборатории есть `C=RU`, у следующего — нейтральный CN без страны. Это **тестовые сертификаты**, не новое удостоверение Howl и не копии production-ключей.

Официальный apksigner строит lineage с порогом33; небольшой Java-проверяющий использует официальный `ApkVerifier` из Android Build Tools. Для каждого API24–36 проверяется валидность подписи и выбранный сертификат: старый до33, новый с33. Отдельно проверяется тестовый предшественник. Исходный реальный APK сравнивается по SHA256 до/после и не изменяется. Тестовые APK/ключи удаляются при завершении; ничего из лаборатории не загружается в Actions artifacts/Releases.

Эксперимент проверяет форматы и выбор подписи официальной библиотекой. Он не выполняет Android PackageInstaller и не доказывает сохранение данных на устройствах. Его фактический результат нужно брать из CI и `rotation-lab-verification.json`, а не из наличия скрипта.

## Что требуется для настоящей смены

1. **Защищённое хранение.** Подтвердить резервную копию прежнего ключа, создать новый production-ключ `CN=Howl` в защищённом контуре, сохранить резервную копию отдельно от CI. Пароли/закрытые ключи не передавать в чат, коммиты, логи или открытые артефакты. Старый ключ сохранить для legacy-подписей.
2. **Настоящая lineage.** Создать old→new lineage официальным apksigner с фактическими двумя ключами. Явно оценить capabilities для installed-data, signature permissions/привилегированных интеграций; не включать rollback к старому ключу автоматически. Пробные ключи из лаборатории не использовать.
3. **Сборочный контракт.** Переделать проверку `tools/verify-release-apk.py`: сейчас она намеренно требует одного прежнего SHA. Будущая политика должна проверять разрешённый старый signer наAPI24–32, новый наAPI33+ и ожидаемую lineage. Проверять также следующий выпуск, не только первый ротированный APK. Новые защищённые секреты добавить отдельно; текущий проверенный путь со старым ключом сохранить до готовности перехода.
4. **Неизменные данные.** Не менять applicationId, minSdk, схемы Room, настройки подписок/профилей/safe-state и общий URL обновлений одновременно с ротацией. Сертификат не должен служить поводом перевыпускать платные подписки или стирать данные.
5. **Приёмка на ОС.** На представителях API24–32 и33+ проверить старые опубликованные APK→новый кандидат→следующий выпуск, встроенное/ручное обновление, профили и подписки, их рабочий резерв, VPN, Always-on при наличии, переход ОС12L→13. Проверить реальные устройства в дополнение к эмуляторам и актуальные новые API сверх лабораторного диапазона, если они поддерживаются. Удаление приложения/очистка данных не является допустимой миграцией.
6. **Восстановление и выпуск.** Откат уже установленного signer/version нельзя свести к возврату старого latest.json. Готовить исправляющий APK с большим versionCode и совместимой lineage. Публикацию проводить после приёмки; новый APK только с новым ключом по общей ссылке сейчас не выкладывать. Перед выпуском сохранить нужные R8 mapping-файлы в защищённом хранилище для диагностики.

## Итог для текущего этапа

Оформление и отсутствие персональных home-путей проверены на кандидате с прежним сертификатом. Для следующего этапа рекомендован совместимый путь к новому активному нейтральному сертификату на Android13+; полноценная ротация production-ключей и миграция пока не выполнены.

[CI 39422732621](https://github.com/mobileproxy/howl-android/actions/runs/39422732621) успешно проверил лабораторию на каждой API24–36: прежний тестовый signer на24–32, новый на33–36. Реальный release-кандидат сохранил прежнюю подпись и SHA256. Это криптографическая проверка официальной SDK-библиотекой, без установки или приёмки сохранения данных. Полный результат — [android-branding-candidate.md](android-branding-candidate.md).
