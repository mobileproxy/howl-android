# Приёмка надёжности Howl Android

Дата комплекта: 27.10.2026. База кандидата: Android 1.0.7 / 826, source `473cdaa58226128ebfd5bfc8dbebb6f16548e9ec`. Это инструкция и безопасный сборщик для будущего согласованного стенда. **Физические H01–H24, установка/обновление, реальный VPN/UDP/звонок, Doze, батарея, сутки работы и цель 30 секунд: NOT_RUN.** Наличие этого файла, успешный fixture или сбор метаданных не меняют данный статус.

Контракт: [дизайн](superpowers/specs/2026-10-27-android-reliability-health-design.md), [план Task5](superpowers/plans/2026-10-27-android-reliability-health.md). Сценарии H01–H24 сохраняют исходные требования программы надёжности; результаты unit/JVM/Robolectric и физических прогонов учитываются отдельно.

## Граница комплекта

Сборщик `tools/collect-reliability-acceptance.py` по умолчанию запускает только встроенный синтетический fixture. Он не устанавливает приложение, не включает VPN, не очищает данные/журналы, не завершает приложение, не меняет настройки ОС/сети/маршруты/профили/подписки, не захватывает трафик и не выполняет сетевые пробы. Нет `logcat`, `bugreport`, `pull`, `run-as`, экспорта приватных файлов, тестовых запросов к серверам или автоматической отправки отчёта.

Режим ADB требует одновременно `--adb`, явный `--serial` одного устройства и `--confirm-read-only`. Автоматического выбора или перечисления устройств нет. Все вызовы используют `adb -s SERIAL`; serial не попадает в JSON. Разрешены только следующие чтения:

| Команда после `adb -s SERIAL` | Что допускается в результате |
|---|---|
| `get-state` | Фиксированный код DEVICE / UNAVAILABLE |
| `shell getprop ro.build.version.sdk` | Число Android SDK |
| `shell cat /proc/uptime` | Монотонный uptime в миллисекундах |
| `shell dumpsys battery` | Процент заряда, код статуса, температура числом |
| `shell dumpsys deviceidle` | Только фиксированные deep/light idle-коды |
| `shell dumpsys package how.vpn.howl` | Только числовой versionCode |

ADB может штатно запустить свой локальный host daemon. Подтверждение доступа к устройству выполняется владельцем на стенде; сборщик не обходит его. После отсутствующего/неподтверждённого `get-state=device` остальные чтения пропускаются. Недоступный вывод остаётся UNKNOWN/UNAVAILABLE, не диагнозом VPN или смерти процесса.

Лимиты: fixture/ConnectionReport-файл до 65536 байт, stdout одной команды до 32768 байт, ожидание одной команды 8 секунд плюс ограниченная уборка локального дочернего процесса, JSON-результат до 16384 байт. На превышение лимита/таймаут частичный stdout отбрасывается; stderr не сохраняется. На ошибке выводится только фиксированный errorCode. Нет автоматических повторов. Сборщик останавливает только собственный локальный процесс чтения при таймауте/переполнении, не Android-приложение.

Ни serial/model/device-name, ни package dump, raw log, OS description/stacktrace, PID/processName/session marker, название профиля/узла, адрес, URL, токен или конфигурация в результат не копируются. Временные исходные stdout находятся только в ограниченной памяти процесса; на диск пишется только перенаправленный пользователем очищенный JSON.

## Запуск без устройства

Из корня исходного репозитория с Python 3.12+:

```bash
python tools/collect-reliability-acceptance.py > acceptance-fixture.json
```

Ожидается exit 0, `mode=FIXTURE`, `physicalAcceptance=NOT_RUN` и все `scenarioStatus.H01`…`H24=NOT_RUN`. Данные устройства в этом режиме вымышленные. Команда проверяет только сам формат/парсер; она не подтверждает работу VPN.

Для очистки уже полученного штатного ConnectionReport JSON без устройства:

```bash
python tools/collect-reliability-acceptance.py --report ./connection-report.json > acceptance-sanitized.json
```

`application.source=SANITIZED_INPUT`, `application.evidence` содержит только allowlist. Метаданные `device` при `mode=FIXTURE` по-прежнему синтетические. Исходный файл не изменяется. Неподдерживаемая схема/нечитаемый/слишком большой файл даёт фиксированную ошибку; сырой текст/путь в JSON не выводятся. Не передавайте в `--report` профили, резервные копии или общий журнал.

Узкие автоматические проверки:

```bash
python -m unittest discover -s tools/tests -p test_collect_reliability_acceptance.py -v
```

ADB в этих тестах заменён на управляемую границу; проверки лимита/таймаута запускают только локальный Python-процесс. Проверки не обращаются к устройству/эмулятору/серверам.

## Будущий явный сбор на согласованном стенде

Этот раздел описывает будущий запуск и не является выполненным действием. Нужны отдельное разрешение на физическую приёмку и уже подготовленное устройство. Установка, обновление, смена сети, создание неисправностей и изменение режима Always-on/lockdown выполняются человеком только в согласованном сценарии; сборщик их не делает.

Задайте serial локально, без отправки в чат:

```bash
HOWL_ACCEPTANCE_SERIAL='serial_согласованного_устройства'
```

Снимок безопасных метаданных перед/после сценария:

```bash
python tools/collect-reliability-acceptance.py --adb --serial "$HOWL_ACCEPTANCE_SERIAL" --confirm-read-only > acceptance-device.json
```

При наличии штатного очищенного ConnectionReport можно добавить `--report ./connection-report.json`. Без него `application.source=UNKNOWN`: метаданные ОС не подтверждают здоровье выбранного выхода. Даже после ADB-сбора все физические H-статусы в JSON остаются NOT_RUN. Реальный вердикт и измерения человек заполняет отдельно по таблице ниже.

Ожидается `mode=ADB_READ_ONLY`, `collectionStatus=OK` либо `PARTIAL`, фиксированные `commandStatus` и только числовые/enum-поля. Exit 0 означает успешное чтение, exit 1 — частичное чтение/неподтверждённый режим/входную ошибку, exit 2 — неверные аргументы, exit 130 — отмену. Ни один из этих кодов не является PASS физической приёмки.

## Что собирается из ConnectionReport

Поддерживается существующий `schema=1`, поля добавлены без экспорта старых приватных данных. Пропущенное/неизвестное поле остаётся неизвестным; парсер не угадывает его по сообщению ошибки.

| Группа | Разрешённые поля и смысл |
|---|---|
| Общие измерения | androidSdk, до 16 probesMs, successfulProbes, downloadBytes до 1 MiB, downloadMs; числовые events.sampledLines/networkChanges/watchdogEvents/coreEvents |
| health | Фиксированные state/cause/systemCause/scope, checkedAgeMs до 120000 или null, temporaryFallback Boolean |
| serviceRecovery | startKind/plannedStop/previousExitKind/previousExitReason; отдельные service/network Attempts/Successes/Cancelled/LastDurationMs |
| recovery | До 8 элементов: cause/result, firstElapsedMs/lastElapsedMs/count/attempts/droppedSummaries; только фиксированные enum-коды и неотрицательные числа |

Recovery count/attempts — накопительные значения эпизода. Повторные snapshots одного эпизода **не суммируются**. `RECOVERED` относится к свежему успешному запросу текущего контекста; запуск ядра сам по себе завершает только service restoration. Историческое время жизни процесса не является временем отсутствия интернета. UNKNOWN/UNSUPPORTED не преобразуется в «убила система». Чужой/старый/future exit record, тот же живой процесс, reboot/сдвиг boot offset или отсутствующая история не доказывают смерть службы.

Успех native-контрольной пробы означает ответ выбранного выхода в пределах доступного API. Он не раскрывает HTTP status/redirect chain и не подтверждает все сайты, UDP, QUIC или каждое split-правило. Успех system/bypass-запроса не доказывает работоспособность VPN-маршрута и не определяет DNS профиля.

## Карточка реального прогона

Для каждого устройства назначьте локальный неперсональный alias D01/D02. В приватном стендовом журнале сохраните соответствие устройству; в итоговую таблицу не переносите serial, модель с пользовательским именем, профили/адреса/узлы/URL. До начала запишите source SHA кандидата и базы, versionCode, SDK, протокол фиксированным кодом, тип сети WIFI/MOBILE, режим Always-on/lockdown, согласие на мобильный резерв и вид сценария. Укажите, кто наблюдал события, длительность и ограничения стенда.

Все временные отметки ниже — монотонные миллисекунды относительно начала сценария. Для сетевого восстановления нужны четыре независимые отметки:

1. `firstFailureMs`: первый наблюдаемый отказ **нового** прикладного запроса.
2. `detectedMs`: подтверждение проблемы клиентом.
3. `fallbackAppliedMs`: фактическое применение проверенного резерва.
4. `freshRequestSucceededMs`: успешный **новый** запрос после применения в актуальном выбранном маршруте.

Время восстановления = `freshRequestSucceededMs - firstFailureMs`, включая обнаружение, проверку резерва и результат. Быстрое выполнение Select или запуск ядра не подменяют последнее событие. Если нужная отметка не наблюдалась — UNKNOWN/NOT_RUN, без расчёта SLA. При отсутствии физического интернета, captive, Doze/сне или здорового разрешённого резерва категория отмечается отдельно; реакцию после возвращения возможности восстановиться считают дополнительно.

Рабочая цель для активного устройства с физическим интернетом и здоровым разрешённым резервом — около 30 секунд от первого отказа до нового успешного запроса. **Данная цель не подтверждена этим комплектом.** Для каждого выполненного сценария также запишите число лишних reload/переключений/закрытых исправных потоков, вмешательств человека, отмен, зависших app-probes, пиковую app-очередь/ownership если метрика доступна, доступность Disconnect и результат проверки маршрутизации. Недоступные метрики остаются UNKNOWN.

Минимальная строка результата без приватных данных:

| deviceAlias | scenario | status | firstFailureMs | detectedMs | fallbackAppliedMs | freshRequestSucceededMs | extraCoreReloads | lostHealthyFlows | userInterventions | evidence |
|---|---|---|---|---|---|---|---|---|---|---|
| D01 | H01 | NOT_RUN | — | — | — | — | — | — | — | — |

PASS разрешён только после выполнения всех критериев строки с наблюдаемыми доказательствами. Если сценарий не удалось создать, сохранить NOT_RUN с фиксированным пояснением ENV_NOT_AVAILABLE/NOT_AUTHORIZED/NO_MATCHING_EVIDENCE. Не выдавать unit trace за физический PASS.

## Always-on/lockdown, батарея и сутки

Повторить применимые H01/H08/H11/H12/H13/H19/H21/H23 отдельно при обычном режиме и при согласованных Always-on/lockdown. Настройки меняет владелец вручную на стенде. При снятии разрешения VPN нет автоматического возобновления против намерения пользователя. Проверять реальные новые запросы в разрешённых маршрутах; зелёный контроль не оправдывает обход защиты.

Для батареи/нагрузки сначала измерить базу при одинаковых устройстве, SDK, типе сети, уровне сигнала, времени экрана, протоколе, сценариях и длительности. Температура/заряд, доступные локальные показатели CPU, app-owned probes, байты и число вмешательств фиксируются численно. Один процент заряда или `dumpsys battery` не измеряет энергопотребление приложения. Этот сборщик не делает сброс/полный экспорт batterystats. Если точной метрики нет — UNKNOWN; процентное «улучшение батареи» не рассчитывается из отсутствующей базы.

Проверки в спокойном режиме не должны превращаться в частый фоновый опрос или полный обход локаций. App coordinator ограничивает только app-owned native-клиентов: 8 actual slots, до 6 non-critical, резерв 2; прежний fuse 12 остаётся отдельной границей. **Независимые native auto/urltest groups имеют собственные single-flight/concurrency10; этот комплект не утверждает единый общий native cap 8.** Для общей нагрузки нужны реальные измерения по всем источникам, включая независимые группы.

Суточный прогон: baseline и candidate в сопоставимых условиях; контроль в начале, после Wi-Fi/mobile/сна/отказа, и в конце. Не собирать полный журнал каждую минуту. Отдельно отметить суммарное активное время, сон, физическое отсутствие интернета и время с запрещённым резервом. До выполненного прогона day/battery/Doze/энергетический эффект остаются NOT_RUN.

## Критерии остановки и итог

При потере/повреждении профиля или рабочего резерва, нарушении DNS/маршрутизации/защиты, применении результата после Disconnect/нового manual intent, новом массовом закрытии исправных потоков или неограниченном росте ресурсов сценарий прекратить и отметить FAIL. Возврат к рабочему состоянию выполняет владелец по отдельно согласованной процедуре; сборщик не откатывает/не переустанавливает приложение и не меняет защиту ради зелёного результата.

По каждому реально выполненному H-сценарию сохранить очищенные snapshots, монотонные отметки, PASS/FAIL/NOT_RUN, недоступные метрики и ограничения. Никакие физические PASS не создаются автоматически. Общий отчёт кандидата должен отдельно перечислять unit/JVM/Robolectric/build и физические свойства. Возможное дополнение PROJECT-HANDOFF.md после согласованной приёмки: ссылка на этот комплект, фактически выполненные устройства/H-сценарии, четыре отметки восстановления, сохранность профилей/ручного намерения/защиты, сравнение с базой и явный список оставшихся NOT_RUN.


Дополнение по диагностике: история причин завершения читается асинхронно одним реальным
worker с дедлайном8с; отсутствие записи остаётся UNKNOWN. Запись маркера и журнала идёт
через отдельные ограниченные IO-очереди и не задерживает «Выключить». При принудительной
смерти процесса или ошибке хранения последняя запись может не успеть сохраниться.
Проверяйте это на стенде; отсутствие записи не доказывает убийство системой. Автоматические
BOOT/PACKAGE_UPDATE/GUARD_RESTART/STICKY не должны отменять сохранённое желание Off.
